一、项目概述
─────────────────────────────────────────────────────────────
基于 LangChain + RAG 技术构建的医疗知识问答 Demo，支持中英文
双语医学问题检索与流式回答。

技术栈:
  - LLM: DeepSeek V4 Flash/Pro (API)
  - Embedding: BGE-M3 (BAAI/bge-m3), 本地 GPU 推理, 1024维
  - VectorStore: Chroma (持久化, langchain-chroma 集成)
  - RAG Chain: LangChain (create_retrieval_chain + ConversationMemory)
  - 后端: Flask REST API (Waitress WSGI 服务器)
  - 前端: Vue 3 + Element Plus + Vite

三、关键问题与解决方案
─────────────────────────────────────────────────────────────

问题 1: LangChain 模块导入失败
  现象: ModuleNotFoundError: No module named 'langchain.chains'
  原因: langchain 1.3.x 将 chains 模块移到了 langchain_classic
  修复: chain.py 中所有 langchain.chains → langchain_classic.chains
        from langchain_classic.chains import (
            create_history_aware_retriever,
            create_retrieval_chain,
        )
        from langchain_classic.chains.combine_documents import (
            create_stuff_documents_chain
        )

问题 2: RAG 检索到文档但回答"无法回答"
  原因: 历史感知检索器 (create_history_aware_retriever) 用 LLM 改写
        问题，改写结果丢失中文导致检索结果不相关
  修复: 去掉了历史感知检索器，直接使用基础 Chroma retriever
        chain.py 中简化了 initialize() 方法：
        - 不再调用 create_history_aware_retriever
        - retriever 直接传入 create_retrieval_chain

问题 3: MMR 检索返回不相关文档
  现象: 检索分数低、结果偏向英文文档，中文问题检索失败
  原因: vectorstore.py 中 search_type="mmr" 适合多样性但不适合
        精准匹配，且 score_threshold 在 MMR 下不生效
  修复: search_type="mmr" → "similarity"
        同时保留 similarity_score_threshold=0.3 过滤低分文档

问题 4: Prompt 变量名不匹配
  现象: "根据现有资料，无法回答该问题"（实际上是 Prompt 没收到问题）
  原因: chain.py 用 input_messages_key="question" 但 Prompt 模板
        中变量名是 {input}
  修复: 统一使用 "input"：
        - prompts.py: {question} → {input}
        - chain.py: input_messages_key="question" → "input"
        - chain.py: invoke({"question": ...}) → invoke({"input": ...})

问题 5: CUDA 兼容性
  现象: 构建向量库时需要 CUDA，但其他人可能没有 GPU
  修复: embeddings.py 添加 auto 检测模式：
        if device == "auto":
            device = "cuda" if torch.cuda.is_available() else "cpu"
        config.py 中 embedding_device 默认值改为 "auto"
        有 CUDA: ~9s/批; 纯 CPU: ~40s/批，自动适配

四、流式输出专项开发记录 (2026-06-10)
─────────────────────────────────────────────────────────────

背景:
  用户要求将问答助手的回答改为逐字流式输出（Server-Sent Events）。
  初始实现后出现三个问题：页面上看不到流式效果、引用来源显示
  过早、LLM 回答中出现"根据您提供的上下文信息"等不当措辞。

架构:
  LangChain LLM.stream()
      ↓ (逐 chunk)
  chain.ask_stream() generator → yield {"type":"token","data":"..."}
      ↓ (每事件 yield → Flask SSE Response)
  Flask /api/chat/stream → SSE (text/event-stream)
      ↓ (Waitress WSGI → Vite proxy → fetch ReadableStream)
  Vue 3 handleSend() → for await (event) → aiMsg.content += event.data
      ↓ (Vue 响应式 → v-html 渲染)
  浏览器逐字显示

问题 6: 页面上看不到流式输出效果（都是一下子输出全部回答）
  ┌─────────────────────────────────────────────────────────┐
  │ 根因: Werkzeug 开发服务器输出缓冲                        │
  │                                                         │
  │ Werkzeug 使用 socket.makefile('wb') 创建输出流，         │
  │ 默认缓冲区 8192 字节。每个 SSE 事件只有 ~60 字节，       │
  │ 事件在缓冲区中累积直到填满 8KB 后才发送到网络。          │
  │ 浏览器一次性收到所有事件，渲染自然是一次性全部显示。     │
  │                                                         │
  │ 排查过程:                                               │
  │ 1. 最初怀疑是前端 token buffer (30ms setTimeout) 导致   │
  │    → 改为直接追加 aiMsg.content，问题依旧               │
  │ 2. 怀疑 Vite 代理缓冲 → 添加 SSE 透传配置，问题依旧     │
  │ 3. 直接请求 Flask 后端测试 → 对端也一次性收到所有事件   │
  │    → 确认是 Flask/Werkzeug 层的问题                     │
  │ 4. 最终定位: Werkzeug wsgiref 的 BufferedWriter 不 flush │
  └─────────────────────────────────────────────────────────┘

  解决方案:
  1. [核心] 替换 WSGI 服务器: Werkzeug → Waitress
     - Waitress 默认 send_bytes=1，不等待积累，每个 chunk 立即发送
     - 单线程 → 4 threads 支持并发请求
     - channel_timeout=120s 适配 SSE 长连接
     启动代码 (app.py):
       from waitress import serve
       serve(app, host=..., port=..., threads=4,
             channel_timeout=120, send_bytes=1)

  2. [辅助] 移除前端的 30ms setTimeout token buffer
     - 原方案用 setTimeout(flushTokens, 30) 批量刷新 token，
       但如果网络一次性交付所有事件，timer 还没触发就全部积压
     - 改为了直接追加: aiMsg.content += event.data
     - 滚动节流: setTimeout → requestAnimationFrame

  3. [辅助] Vite 代理 SSE 透传配置 (vite.config.js)
     - 为 text/event-stream 响应添加 flushHeaders 钩子

  变更文件:
  - backend/app.py: 安装 waitress 包, 修改启动逻辑, 移除 Connection 头
                    (WSGI PEP 3333 禁止应用设置 hop-by-hop 头)
  - frontend/src/views/ChatView.vue: 移除 token buffer, 直接追加
  - frontend/vite.config.js: 添加 SSE 代理透传配置

问题 7: 思考/生成过程中"引用来源(5)"过早显示
  现象: 发送问题后约 2 秒（检索完成），AI 消息气泡尚未有任何内容，
        但"引用来源(5)"按钮已出现
  原因: SSE 事件顺序 — sources 事件最先返回（检索阶段），前端在
        handleSend() 中直接 aiMsg.sources = event.data 立即显示
  解决方案:
    ChatView.vue 中改为延迟应用来源:
    - sources 事件到达时存入 pendingSources，不直接设置 aiMsg.sources
    - 首个 token 事件到达时才将 pendingSources → aiMsg.sources
    - 兜底: done/error 时若仍未应用则补上

  变更文件:
  - frontend/src/views/ChatView.vue: handleSend() 中的事件处理逻辑

问题 8: LLM 回答措辞不当
  现象: 回答中出现 "根据您提供的上下文信息，没有直接提及..."
        这样的措辞
  原因: System Prompt 中写的是 "你的任务是基于提供的上下文信息..."
        LLM 自然回显了 Prompt 中的用语
  解决方案:
    - "上下文信息" → "已有文献资料"
    - 新增规则 7: 明确禁止使用 "根据您提供的上下文信息"、
      "根据上下文"、"基于提供的资料" 等措辞
    - 引导 LLM 改用 "根据现有文档"、"已有研究显示"、"资料表明" 等

  变更文件:
  - prompts/rag_system.txt: 重写系统提示词
  - backend/assistant/prompts.py: 同步更新默认 fallback 提示词

  验证: 测试 "鼻炎怎么治疗？" → 回答中不再出现旧措辞 ✓


五、DeepSeek 模型配置与切换
─────────────────────────────────────────────────────────────
环境变量 (.env):
  DEEPSEEK_MODEL=deepseek-v4-flash        # 当前使用 Flash
  DEEPSEEK_THINKING=disabled              # 关闭思考模式(减少延迟)
  DEEPSEEK_REASONING_EFFORT=low           # 合法值: low/medium/high/max/xhigh
                                          # 注意: langchain-openai 1.2.2 无条件
                                          # 发送 reasoning_effort, 不能为 None/off

模型对比:
  | 指标        | V4 Pro (thinking=enabled) | V4 Flash (thinking=disabled) |
  |-------------|---------------------------|------------------------------|
  | first token | ~5.5s                     | ~4.25s                       |
  | 总时间      | ~11s                      | ~8.2s                        |
  | tok/s       | 44                        | 44                           |
  | 价格        | $1.74/$3.48 per 1M        | $0.14/$0.28 (便宜 12×)       |

切换到 V4 Pro 深度推理: 修改 .env 中 DEEPSEEK_MODEL 和 DEEPSEEK_THINKING 即可

踩坑记录:
  1. langchain-openai 1.2.2 无条件将 reasoning_effort 放入 API payload
     → reasoning_effort 不能为 None 或 "off"，必须传合法值
  2. extra_body={"thinking":{"type":"disabled"}} 与 reasoning_effort
     同时存在时 DeepSeek API 返回 400
     → thinking=disabled 时不传 extra_body，只保留 reasoning_effort=low
  3. Flask debug mode reloader 检测到 site-packages 文件变化时会在
     流式请求中途重启服务器，导致 ConnectionResetError
     → 使用 Waitress 替代 Flask 内置服务器（Waitress 无 watchdog）
